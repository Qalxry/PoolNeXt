# Strategy Decision Guide

## 定量决策框架

### 步骤 1：计算可复用率

```
可复用行数 = Σ (模块行数 × 复用系数)

复用系数:
  ✅ 无变化    → 1.0
  🟢 小改      → 0.9
  🟡 中改      → 0.5（骨架复用，逻辑重写）
  🔴 大改      → 0.2（仅模式/框架代码可参考）
  ❌ 删除      → 0.0

可复用率 = 可复用行数 / 总行数
```

### 步骤 2：选择策略

| 可复用率 | 推荐策略 | 理由 |
|---------|---------|------|
| < 30% | 从零重写 | 旧代码更多是负担而非资产 |
| 30-70% | 分阶段 SPEC 对齐 | 基础设施保留，业务逻辑重构 |
| > 70% | 按 proposal 逐条修 | 大部分代码不需要动 |

### 步骤 3：验证决策

回答以下问题来确认策略选择：

**如果选择了"从零重写"，确认：**
- 旧代码的 DB 连接/ORM 模式确实不可复用？
- 旧代码的协议适配层（API/WebSocket/ACP）确实不可复用？
- 旧代码的配置加载/校验框架确实不可复用？
- 有足够的工程时间重写这些基础设施？

如果有 ≥2 项可复用 → 考虑降级为"分阶段对齐"。

**如果选择了"按 proposal 逐条修"，确认：**
- 各 proposal 之间没有交叉依赖？
- 没有跨模块的数据模型变更？
- 没有需要多个模块同步修改的架构变更？

如果有 ≥1 项不满足 → 考虑升级为"分阶段对齐"。

## 常见场景

### 场景 A：V0 刚写完，代码量小，缺陷多

**典型指标**: ~5K-10K 行，大量 P0/P1 缺陷，架构级 FP 提案。

**推荐**: 分阶段 SPEC 对齐。理由：代码量小意味着复用的代码绝对量也不大，但基础设施骨架（DB/API/config 框架）重写纯属浪费。

### 场景 B：成熟项目，局部重构

**典型指标**: ~50K+ 行，1-3 个模块需要重写，其余稳定。

**推荐**: 按 proposal 逐条修 + 重点模块的小型分阶段计划。

### 场景 C：技术栈迁移

**典型指标**: 语言/框架/数据库变更。

**推荐**: 从零重写，但参考旧代码的架构决策和领域模型。

## "基础设施骨架"的判定标准

以下代码属于基础设施骨架，即使业务逻辑需要重写也值得保留：

| 类别 | 示例 | 复用价值 |
|------|------|---------|
| 数据库连接 + ORM | SQLite 初始化、WAL 配置、事务管理 | 高：与业务无关的通用代码 |
| Repository 模式 | CRUD 基类、mapper 层、行映射 | 高：模式可复用，具体查询调整 |
| API 框架 | Express 路由注册、auth 中间件、分页 | 高：HTTP 层与业务逻辑解耦 |
| Protocol adapter | ACP 连接、进程管理、消息序列化 | 高：协议对接是稳定层 |
| Config system | YAML 加载、Zod schema、preset 解析 | 中：schema 变但加载框架不变 |
| Event system | EventEmitter 封装、事件发射管道 | 中：增加事件类型但管道不变 |
| File system utils | safe-path、worktree 操作封装 | 高：纯工具代码 |
| Test infrastructure | Test setup、fixture 加载、mock 工厂 | 中：测试骨架可复用 |
